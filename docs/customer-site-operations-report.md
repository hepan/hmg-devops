# 客户现场私有化运维监控系统：项目范围与能力汇报

> 内部讨论稿。本文汇总已确认的产品范围与建议能力，不代表选型、技术验证或开发承诺。目标是决定是否开展现场盘点和技术验证，再决定开发。

## 结论

建议规划一套**每家医院独立运行**的院内运维监控系统：每台受监控服务器部署采集 Agent，院内汇总端展示状态、历史与告警；确定性故障由规则判断，筛选后的异常日志交给院内无显卡 CPU 小模型辅助判断。系统以公司自有服务、专用中间件及其宿主机为边界，运维人员为公司具名管理员。模型、组件和接口实现均未选定。

## 现场规模与边界

| 场景 | 通常相关服务器数量 | 常见部署形态 |
| --- | --- | --- |
| 小医院 | 2–3 台 | 多项自有服务集中部署，可随新增产品扩容 |
| 大医院 | 通常不超过 20 台 | Oracle 专用服务器、MinIO 存储服务器、业务／中间件服务器及若干运行 C++ 程序的 Windows 服务器 |

目标环境包括 Windows Server 2008/2012/2016/2019、CentOS 7、龙蜥（用户提及 7.9/8.10；版本与兼容性需核实）。监控自有非容器化服务，及实际部署使用的 Oracle、RabbitMQ、Redis、MinIO、Nginx 等专用中间件。不监控 HIS 或院内集成平台自身，也不监控与其对接故障。不提供远程启停、执行脚本或改配置能力。[监控范围决策](https://github.com/hepan/hmg-devops/issues/2)

## 产品能力

### 采集、健康与状态

每台受监控机器一个 Agent，采集主机资源、服务状态、必要中间件指标和指定日志；同机多个自有服务共用 Agent。主机指标类别参考 Linux node_exporter 与 Windows windows_exporter，但不承诺照搬所有指标或旧系统已兼容。中间件除运行状态外需覆盖与实际使用相关的信号，例如 Oracle 表空间和 RabbitMQ 队列消息数量。Agent 失联、指标缺失须标为**未知**，不能归零或标正常。[Agent 边界](https://github.com/hepan/hmg-devops/issues/5) · [监控信号](https://github.com/hepan/hmg-devops/issues/6)

新开发或修改的自有服务应提供反映**核心职责可用性**的健康检查能力，由本机 Agent 定时调用；关键专用依赖不可用可使服务报告不健康。检查超时先标未知；无接口的旧服务仅能显示“进程运行，实际可用性未验证”。健康检查与日志分析并行，不要求旧服务立即改造。[健康检查决策](https://github.com/hepan/hmg-devops/issues/14)

院内界面按服务器、服务和中间件查看当前状态、指标近期趋势和最后成功采集时间；按时间、对象查看历史告警、通知结果、人工处理记录与关联的指定日志。不要求跨医院联网实时总览或全院日志全文搜索。Agent 支持管理员在院内提供更新包后主动一键更新选定机器，逐台展示结果；失败机器应保留原版本，机制未验证。[展示范围](https://github.com/hepan/hmg-devops/issues/9)

### 告警与本地小模型

- **规则路径**：服务停止、已有健康检查明确失败、专用中间件不可用，以及资源指标达到现场配置条件并持续一段时间后告警。普通波动仅展示。单次检查超时不直接认定服务故障。
- **日志路径**：只读取指定的自有应用日志、必要的专用中间件错误日志及相关 Windows 事件日志；先按事件类别、等级与上下文预筛，**不把全部日志交给模型**。院内 CPU 小模型主要归并并解释候选错误，可判断规则未覆盖的异常是否值得正式告警。告警系统创建记录并按现场配置通知，标注“模型判断，待人工核实”。模型不直接发送通知，不能否决规则告警，也不能把推测写成确认根因。
- **失效与跟进**：模型无响应时规则和普通状态查看继续，候选日志标待分析；同一次持续异常按一件故障跟进。告警、邮件投递、公司人员已接手、信号已恢复与人工确认已结束分别记录。需区分及时处理的故障与需关注的风险，不在此确定阈值和去重算法。

[告警流程决策](https://github.com/hepan/hmg-devops/issues/7) · [模型能力决策](https://github.com/hepan/hmg-devops/issues/8)

### 通知、日报和公司项目记录

每院每天生成院内状态汇总，平稳日也显示采集缺口，不能把“无告警”写成“所有服务正常”。日报概括当前状态、指标变化、当天出现／恢复／未结束告警与待分析事项；不代替实时告警。邮件只含摘要、时间、数量和必要的院内记录引用，不发送原始日志或患者资料。客户现场须提供获批准且实际可用的出站通道；无出口时院内仍可见，但不承诺公司人员收到邮件，投递失败与告警分别可见。[邮件出口](https://github.com/hepan/hmg-devops/issues/3) · [日报范围](https://github.com/hepan/hmg-devops/issues/10)

有合规通道时，可将安全的每日摘要自动归档到**明确关联的公司内部项目**，供项目负责人了解状态与未结束问题；无通道或无法匹配项目时显式标记未归档。不自动创建或流转维修工单；不向公司系统传原始日志、患者资料或院内不可访问的详情链接。[项目系统边界](https://github.com/hepan/hmg-devops/issues/11)

## 日志规范建议与人员责任

新开发或修改的自有服务遵循[标准化日志建议稿](https://github.com/hepan/hmg-devops/blob/prototype/logging-standard-draft/docs/prototypes/logging-standard-draft.md)：**不强制 JSON 格式**，统一可识别的时间、服务身份、等级、描述及关键运维事件类别；各产品提交脱敏样例和格式映射。写日志前排除或替换患者健康资料与凭据；旧服务暂不强制改造。稳定事件类别用于预筛和归并，事件出现不等于自动告警。

公司具名管理员统一查看、配置和跟进告警；需医院执行操作时线下联系。系统不预设厂商公网登录入口，也不在本次规划细粒度角色体系。[责任边界](https://github.com/hepan/hmg-devops/issues/4)

## 风险与下一步验证

1. **环境兼容**：旧版 Windows、CentOS、龙蜥的采集权限与健康检查接入方式未验证；现有服务是否能提供健康接口需现场盘点。
2. **资源与可靠性**：无显卡 CPU 小模型的延迟、内存占用、并发及误判率未测；Agent 升级失败保留旧版、汇总端故障时的数据补回能力未验证。不能承诺零丢失。
3. **日志与敏感信息**：各产品现有格式是否能稳定提取约定语义、异常文字是否夹带患者数据需验证；原始日志留存与脱敏机制尚未设计。
4. **对外通道**：逐院确认邮件中继及公司项目系统可达性、项目标识匹配与数据出境边界；完全隔离现场不承诺外部自动同步。

**建议的下一步决定**：认可上述范围后，安排代表性大小医院的部署与日志盘点，验证兼容性、模型资源消耗、敏感信息处理及外发通道；根据验证结果另定产品实施方案与开发计划。本报告不批准具体模型、技术栈、预算或迭代排期。
