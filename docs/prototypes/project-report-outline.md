# 客户现场运维系统：内部汇报结构原型

> 讨论用大纲，不是最终报告，也不是开发立项或技术验证结论。

## 1. 一页结论与待讨论事项

- 为什么做：公司产品私有化部署后，运维人员需要在隔离环境及时了解服务、专用中间件和服务器状态。
- 本次讨论的边界：每院独立；采集 Agent + 院内汇总 + 确定性告警 + 日志小模型辅助；邮件与公司项目归档依赖现场通道。
- 向管理层提出的问题：是否认可此产品范围，后续是否安排现场调研、兼容性验证与开发规划；本报告不提出未经测量的性能承诺。

## 2. 典型现场和要监控的对象

小医院约 2–3 台，大医院通常不超过 20 台，随新增本公司产品扩容。Windows Server 2008/2012/2016/2019、CentOS 7、龙蜥；运行本公司非容器化服务、Oracle、RabbitMQ、Redis、MinIO、Nginx 等。不纳入 HIS/院内平台自身和对接故障。

## 3. 产品能力地图（建议一张竖向图）

每台机器的采集 Agent → 该医院的院内汇总端 → 状态、趋势和历史告警。Agent 分别采集主机／中间件指标、指定日志，并定时调用自有服务健康检查接口。明确故障和持续超限走规则；筛选后的日志进入院内 CPU 小模型，模型来源告警标注待人工核实。Agent 支持现场主动一键更新并逐机报告结果。

## 4. 运维人员一天的使用情景

白天：收到明确故障或模型来源告警 → 院内查看证据与关联日志 → 公司人员标记接手并跟进 → 信号恢复与人工结束分开记录。每日：院内生成状态汇总；即使无告警也标出数据缺口。有合规出口才发邮件，并可能把安全摘要归档到明确关联的公司项目；没有出口时院内可见，不宣称外部送达。

## 5. Agent 与小模型各自的非能力

Agent 失联不等于服务器宕机；旧服务无健康接口时进程运行不代表实际可用。模型主要分析候选异常日志，不参与 CPU/内存阈值判断，不能否决规则告警，也不能将推测写成已确认根因。模型不可用时规则监控继续、日志标待分析。

## 6. 日志与健康接口建议

自有新开发或修改服务遵循[标准化日志建议稿](https://github.com/hepan/hmg-devops/blob/prototype/logging-standard-draft/docs/prototypes/logging-standard-draft.md)：不强制 JSON，统一最低语义及少量稳定运维事件；写日志前排除患者资料与凭据。新改服务提供体现自身核心职责的健康检查，旧服务逐步适配。

## 7. 风险、假设与下一步验证清单

- 旧 Windows / CentOS / 龙蜥采集可行性与安全约束未验证。
- 无显卡 CPU 模型的延迟、资源占用和误判率未测量。
- Agent 更新失败保留旧版、院内汇总故障时补回数据的能力未验证。
- 各产品日志格式能否稳定提取语义，以及现有服务是否具备健康接口，需盘点。
- 邮件出口及公司项目归档通道按现场确认；日志敏感内容、摘要边界需验证。

## 8. 本次不决定的事项

不选具体组件／模型，不出实施架构、开发排期或预算，不实施系统，不接管医院其他系统，不提供远程启停或脚本执行。
